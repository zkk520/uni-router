# 路由语义设定

本文档记录 uni-router 路由配置的产品语义，用于统一前端展示、文案说明和后端行为理解。

核心目标是把两类路由心智分开：

- **主备模式**：关注“谁是主端点，失败后按什么固定顺序备用”。
- **加权分流**：关注“请求按什么比例分配给多个端点”。

## 1. 术语表

### 1.1 主备模式

当前代码中的 `manual` 模式，在产品语义上应理解为“主备模式”或“顺序模式”。

用户心智：

> 平时优先使用主端点；如果开启故障转移，主端点失败后按备用顺序继续尝试其他端点。

主备模式关注固定顺序，不关注流量比例。

### 1.2 加权分流

当前代码中的 `weighted` 模式，在产品语义上应理解为“加权分流”。

用户心智：

> 多个端点一起承担请求；权重越高，越容易优先被选中。

加权分流关注请求比例，不关注固定主备顺序。

### 1.3 首选端点

`preferred_endpoint_id` 表示“首选端点”，不应称为“当前使用”。

原因：

- 它是用户配置的优先尝试目标，不代表系统当前正在处理某个请求的实时端点。
- 请求成功或失败不会自动改写 `preferred_endpoint_id`。
- 它主要在主备模式下影响首个尝试端点；加权分流下不应作为核心概念展示。

推荐 UI 文案：

- “首选端点”
- “主端点”
- “设为主端点”

不推荐 UI 文案：

- “当前使用”
- “当前端点”

### 1.4 顺序 / priority

`priority` 表示主备模式下的端点顺序。

它回答的问题是：

> 在主备模式中，谁先尝试，谁后尝试？

推荐 UI 文案：

- “顺序”
- “主备顺序”
- “备用顺序”
- “尝试顺序”

不推荐 UI 文案：

- “优先级”单独裸露展示，除非同时解释“数字越小越靠前”。

### 1.5 权重 / weight

`weight` 表示加权分流模式下的流量比例。

它回答的问题是：

> 平时请求大概分给谁多少？

权重不要求总和为 100。前端可以根据总权重显示预计占比。

示例：

| 端点 | 权重 | 预计占比 |
|---|---:|---:|
| A | 70 | 70% |
| B | 20 | 20% |
| C | 10 | 10% |

### 1.6 故障转移

`failover_enabled` 表示：

> 当前候选端点请求失败后，是否继续尝试后续候选端点。

故障转移不是选择算法本身，也不是“是否启用顺序”。

- 在主备模式中，候选顺序来自主备顺序。
- 在加权分流中，候选顺序来自本次请求按权重生成的动态候选队列。

## 2. 模式定义

### 2.1 主备模式

主备模式使用固定顺序。

示例配置：

```text
模式：主备模式
顺序：A -> B -> C
首选端点：A
```

#### 故障转移关闭

```text
请求 -> A
A 成功 -> 返回成功
A 失败 -> 返回失败
```

用户理解：

> 我只想使用主端点；主端点失败时不要自动切换。

#### 故障转移开启

```text
请求 -> A
A 成功 -> 返回成功
A 失败 -> B
B 成功 -> 返回成功
B 失败 -> C
C 成功 -> 返回成功
C 失败 -> 返回最终失败
```

用户理解：

> 平时使用主端点；主端点失败时按备用顺序兜底。

### 2.2 加权分流

加权分流使用动态候选顺序。

示例配置：

```text
模式：加权分流
A 权重：70
B 权重：20
C 权重：10
```

大量请求下，预期效果接近：

```text
A 约 70%
B 约 20%
C 约 10%
```

单次请求并不保证固定顺序。系统会为每次请求按权重生成一个候选队列。

例如某次请求生成：

```text
A -> B -> C
```

另一次请求可能生成：

```text
B -> A -> C
```

#### 故障转移关闭

目标语义：

```text
按权重生成本次候选队列
尝试队列中的第一个端点
第一个端点成功 -> 返回成功
第一个端点失败 -> 返回失败
```

用户理解：

> 每次请求按权重选择一个端点；如果选中的端点失败，不继续尝试其他端点。

#### 故障转移开启

目标语义：

```text
按权重生成本次候选队列
尝试队列中的第一个端点
第一个端点失败 -> 尝试队列中的下一个端点
直到成功或所有候选都失败
```

用户理解：

> 平时按权重分流；如果本次选中的端点失败，继续尝试本次候选队列中的其他端点。

加权分流的故障转移顺序不应使用 `priority`。否则用户会同时面对“权重”和“顺序”两个选择规则，容易混淆。

## 3. 字段职责边界

| 字段 | 产品名称 | 主备模式 | 加权分流 |
|---|---|---|---|
| `mode` | 路由模式 | `manual` 对应主备模式 | `weighted` 对应加权分流 |
| `preferred_endpoint_id` | 首选端点 / 主端点 | 影响首个尝试端点 | 不作为核心概念展示 |
| `priority` | 主备顺序 / 尝试顺序 | 决定固定候选顺序 | 不作为路由语义展示 |
| `weight` | 权重 / 预计占比 | 不展示或弱化 | 决定动态候选顺序 |
| `failover_enabled` | 故障转移 | 失败后是否按顺序继续 | 失败后是否继续尝试动态候选队列 |

## 4. 前端展示规则

### 4.1 主备模式展示

主备模式应突出“顺序”和“主端点”。

建议展示：

```text
#1 A 主端点
#2 B 第一备用
#3 C 第二备用
```

当故障转移关闭时，说明：

```text
仅尝试主端点。备用端点不会在请求失败后自动使用。
```

当故障转移开启时，说明：

```text
请求优先发送到主端点；失败后按顺序尝试备用端点。
```

主备模式下可以保留拖拽排序。拖拽文案建议为：

```text
拖动调整主备顺序
```

### 4.2 加权分流展示

加权分流应突出“权重”和“预计占比”。

建议展示：

```text
A 权重 70，预计 70%
B 权重 20，预计 20%
C 权重 10，预计 10%
```

说明文案：

```text
按权重为每次请求生成候选顺序。权重越高，越容易优先尝试。
```

如果故障转移开启，补充：

```text
所选端点失败后，会继续尝试本次候选队列中的其他端点。
```

加权分流下不应强调：

- `#1` / `#2` / `#3` 形式的固定优先级
- “主端点”
- “当前使用”
- “拖动调整优先级”

如果仍保留拖拽，只能表达为：

```text
拖动调整显示顺序
```

### 4.3 “当前使用”文案替换

所有路由配置页中的“当前使用”应逐步替换为“首选端点”或“主端点”。

原因：

- “当前使用”容易被理解为实时运行状态。
- 实际字段 `preferred_endpoint_id` 是配置项，不是运行时观测值。

## 5. 当前代码行为对照

### 5.1 数据模型

参考文件：

- `internal/model/route.go`

当前模型字段：

```go
type RouteProfile struct {
    Mode                RouteMode
    PreferredEndpointID int
    FailoverEnabled     bool
    Endpoints           []RouteEndpoint
}

type RouteEndpoint struct {
    Priority int
    Weight   int
    Enabled  bool
    Status   RouteEndpointStatus
}
```

当前模式：

```go
RouteModeManual   RouteMode = "manual"
RouteModeWeighted RouteMode = "weighted"
```

产品文案可以改为“主备模式 / 加权分流”，但 API 字段值不需要立即改名。

### 5.2 候选选择

参考文件：

- `internal/op/route.go`

当前候选选择大致流程：

1. 优先选择 `enabled == true` 且 `status != error` 的端点。
2. 如果没有可用的非 error 端点，则退回到所有 enabled 端点。
3. `weighted` 模式直接返回 `weightedEndpointOrder(enabled)`。
4. `manual` 模式按 `priority` 升序排序。
5. 如果存在 `preferred_endpoint_id`，将该端点移动到候选队列第一位。
6. 如果 `failover_enabled == false`，manual 模式只返回第一个候选端点。

### 5.3 加权候选顺序

参考文件：

- `internal/op/route.go`

当前 `weightedEndpointOrder` 会复制端点列表，先随机打乱，再按权重做随机排序。

产品语义应解释为：

> 每次请求按权重生成一个动态候选顺序；权重越高，越容易排在前面。

### 5.4 转发与故障转移

参考文件：

- `internal/relay/route.go`

当前转发流程会按候选队列依次尝试端点。

转发失败后：

- 如果响应已经写出，停止继续尝试。
- 如果 `failover_enabled == false`，停止继续尝试。
- 否则继续尝试下一个候选端点。

注意：转发前校验失败，例如 channel/key 不可用、类型不兼容，会记录为 skipped 并继续看下一个候选。该行为与“故障转移关闭时只尝试一个端点”的严格产品语义略有差异，后续如需强一致，需要单独评估是否调整后端。

## 6. 后续改造建议

### 6.1 前端优先改造

建议先改 UI 文案和展示规则，不立即改 API 字段名。

优先级：

1. 将模式文案从“手动 / 加权”调整为“主备模式 / 加权分流”。
2. 将“当前使用”调整为“首选端点”或“主端点”。
3. 主备模式显示 `#1 / #2 / #3` 顺序，并解释故障转移开启/关闭的效果。
4. 加权分流显示权重和预计占比，不显示固定优先级。
5. 根据模式调整拖拽提示：主备模式为“调整主备顺序”，加权分流为“调整显示顺序”。

### 6.2 后端一致性评估

后续如果要让产品语义与后端行为完全一致，需要评估：

1. 加权分流且 `failover_enabled == false` 时，是否应该只保留一个候选端点。
2. 转发前 skipped 场景是否也应该受 `failover_enabled` 限制。
3. `preferred_endpoint_id` 在加权分流下是否应被忽略、保留，或仅用于模型列表等非请求转发场景。

这些属于行为变更，应在 UI 文案调整之后单独规划。

## 7. 推荐总结

最终对用户解释时，可以压缩为：

```text
主备模式：按固定顺序尝试端点。故障转移关闭时只用主端点；开启后主端点失败会按顺序尝试备用端点。

加权分流：按权重为每次请求生成候选顺序。权重越高，越容易优先尝试；开启故障转移后，失败会继续尝试本次候选队列中的其他端点。
```

对应字段职责：

```text
priority = 主备顺序
weight = 加权比例
preferred_endpoint_id = 首选端点
failover_enabled = 失败后是否继续尝试
```
